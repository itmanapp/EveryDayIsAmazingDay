# Spec 與小張 Task

## Spec

以 BRIEF 的確定決策及已檢查的程式為根據，套用 SPEC 範本。Spec 描述使用者可觀察的行為、模組責任與公開契約；具體待改檔案放在 Task 並在實作前再次查證。

每個驗收條件使用穩定 ID `AC-001`，以 Given／When／Then 或同等明確形式寫出輸入、觸發與結果。避免「快速」「友善」「正確」等無法單獨判斷的詞；效能需求附資料量、環境、量測方式和門檻。先寫正常情境，再補與本專案風險相關的錯誤、權限、資料與重試情境。

測試策略列出公開觀察邊界（例如 HTTP API、CLI、公開服務介面）、AC 對應的測試層級、資料與外部依賴的處理。優先選能穩定驗證需求的少量邊界；只有必要時才加更低層的細粒度測試。UI 視覺與可及性需求另外記錄適合的實際檢查，不假裝單元測試已涵蓋。

Spec、測試邊界與 Task 清單可一起確認。後续在同一邊界增加已授權行為的測試不必重問；改變核心公開契約時走需求變更流程。

## Task 的切法

一張 Task 交付一小段可示範或驗證的完整行為，包含所需資料、邏輯、介面及測試。不是依「資料庫全部／後端全部／前端全部／最後寫測試」切四張。

例如「使用者新增一則便條，重啟後仍可列出」是完整行為；「建好資料表」單獨通常尚未有可驗收的使用者成果。第一張優先打通最薄的一條真實路徑，再加入錯誤、權限或其他增量。

粒度以新 AI 在一個工作階段內能讀完、實作並驗證為準。若有多個互不相干成果、未知架構決策或龐大修改範圍，繼續拆小，不用估計行數作唯一標準。

必要的環境建置或調查可獨立成 `setup`／`spike` Task，但必須有可驗證產出、停止條件與後續關係。spike 的結果是決策或證據，不可因原型可跑就宣稱功能完成。跨全域機械遷移可依「先相容擴充 → 分批遷移 → 移除舊介面」拆解，讓每步可驗證。

## 每張 Task 應可獨立接手

使用 TASK 範本，至少包含：

- ID、名稱、類型、狀態、所依據 Spec 版本。
- 交付行為、AC ID 及本張的具體完成範圍，並註明不做什麼。
- `depends_on` 明確列出其他 Task ID；沒有就是空清單。
- 必要上下文、預計觸及的模組與公開介面。
- 如何先重現失敗、在哪個邊界測、如何跑測試與回歸。
- 完成條件：行為通過、所需測試實跑、兩軸 Review、文件與 STATE 更新。

先檢查依賴是否真的阻擋開工；不能因編號較小就一律相依。確認沒有不存在的 ID、自我相依或循環。所有依賴完成後才能領取。

TASKS 中維持 AC → Task → 預期測試的對照。每個範圍內 AC 至少有一張明確負責驗收的 Task；若跨多張 Task，指出最後負責整合驗證者，不能各自假設另一張會測。`ready` 表示單張已寫完整，不表示全域授權與相依條件可略過。

規劃交付前，依 [validation.md](validation.md) 檢查穩定欄位、AC 覆蓋及相依關係，並核對根目錄的專案工作流程摘要。給使用者簡短清單：流程摘要、Spec 版本、範圍、各張交付與阻擋關係、待決事項。若實作已授權且達到 ready，記錄後進入任務迴圈；只要求規劃則停在文件交付。
