# 以 TDD 完成一張 Task

讀當前 Task、Spec、PROJECT 的真實命令與現有測試。此流程採小步 **Red → Green**，集中重構放在 Review 階段；每次重構後保持測試為綠。

## 開工基準

記錄 branch、HEAD、工作區中既有修改和本張的預期範圍。沒有 commit 或沒有 Git 時，保存相關檔案的前置快照／雜湊和清單。保護使用者已有變更，不用 reset 或清理指令取得「乾淨」狀態。

先跑足以辨認基線的相關測試。既有失敗須記錄命令、錯誤及與本 Task 的關係；不能在交付時隱藏，也不能隨意擴張去修不相關問題。

## 每次只處理一個行為

1. **選行為**：從本張 AC 選尚未完成的最小行為，先選能打通流程的正常情境。
2. **Red**：在約定公開邊界寫一個測試並立即執行。記錄命令、exit code、關鍵輸出、失敗斷言與原因。失敗必須因目標行為未實作或錯誤；工具不存在、依賴未裝好、拼字錯誤及任意拋錯不能作為有效 Red。空專案可先做最小可執行腳手架，但不能偷放將驗證的功能。
3. **Green**：只補足該行為需要的實作，執行相同測試並確認通過。若測試一開始就是綠，確認行為是否已存在或測試未能捕捉缺陷；如實記為既有覆蓋，不捏造 Red。
4. **循環**：接著加入重要的錯誤或邊界行為，每個都先 Red 再 Green。不要先寫完全部測試再一次完成全部程式。
5. **回歸**：跑 Task 涉及的測試群與必要靜態檢查，再進 Review。整體全套檢查至少在最後整合交付時執行。

## 測試品質

- 從公開 API、CLI 或服務介面觀察結果；不要直接呼叫 private 方法或斷言內部呼叫順序。
- 預期值來自 Spec、已知算例或獨立資料，不能重寫同一段演算法當 oracle。
- 外部網路、時鐘、隨機值等可用可控制的替身；不要 mock 掉本次要驗證的業務規則。重要 adapter 要有適合的整合測試。
- 持久化需求使用隔離的真實暫存儲存，依需求驗證重啟讀取；不能只對 mock storage 宣稱真實持久化通過。
- 修 bug 先用回歸測試重現。新失敗要確認是哪個行為與哪次變更導致，再修正。

## 證據

使用 TDD 範本記錄每一輪的 AC、測試位置、Red／Green 命令、exit code、關鍵結果及被測版本。可將大量輸出放進專案 `docs/workflow/evidence/` 並以相對路徑引用；不保存金鑰、個資或無關環境輸出。

證據必須來自實際執行。沒有 shell／依賴／服務時標記「未執行」與原因，Task 保持未完成，列出恢復命令。

純文件或低風險設定的 Task 不強造 Red。列出 TDD 不適用的具體理由，改用可重現的文件連結檢查、設定解析、dry run 或人工檢查紀錄；仍須 Review。帶有程式邏輯的設定／腳本要依實際風險驗證，不能用「設定檔」一詞跳過測試。
