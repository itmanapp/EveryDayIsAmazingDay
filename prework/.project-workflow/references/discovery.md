# 盤點與需求釐清

## 先找事實

讀取目標專案的規則、README、依賴清單、測試與 CI 設定、既有介面、領域詞彙及 ADR。記錄哪些來自檔案、哪些是使用者提供、哪些是推測。

空專案先辨認現有工具，不先替使用者選框架；等平台與行為明確後，提出能滿足需求的簡單方案。若有既有專案，優先沿用其慣例。可自行查證的版本、檔案與執行指令不丟回給使用者。

將套件管理器、語言版本、安裝／啟動／單檔測試／全套測試／build／lint／型別檢查記在 PROJECT，附各自工作目錄。尚未有命令時寫「待建立」；工具不可用時寫「不可用及原因」。不可用不等於不適用。

## 用分輪訪談釐清

每輪以 1–3 個會改變設計的問題為主，附推薦選項與取捨。只有前置決策已確定的問題才進本輪，不同時問依賴未知答案的下游問題。收到答案後立即更新 BRIEF。

依專案需要涵蓋：

| 面向 | 要釐清的具體事情 |
| --- | --- |
| 問題與成功 | 誰現在遇到什麼困難？做完後可觀察到哪個改善？ |
| MVP 範圍 | 第一版必須有哪些行為？哪些明確不做？ |
| 角色與權限 | 誰能操作／讀取哪種資料？是否區分擁有者或租戶？ |
| 主要流程 | 從哪裡開始、輸入什麼、看到什麼、完成後狀態如何？ |
| 例外與邊界 | 空資料、無效輸入、重複操作、部分失敗如何處理？ |
| 資料 | 來源、保存、刪除、備份或遷移需求是什麼？ |
| 環境與限制 | Web／行動／CLI？既有系統、技術限制、期限與預算？ |
| 品質 | 適用的效能、安全、可及性、可靠性門檻如何驗證？ |

用具體反例測試共同理解：「新增成功後立刻重開，資料應該還在嗎？」比「需要持久化嗎？」更容易得到有效答案。與既有程式不符時，指出差異並釐清期望，而非默默採一方。

問答使用 Q-001 等穩定 ID。未決事項分為：

- **blocking**：會改變核心行為、資料或驗收；相關工作保持 draft。
- **assumption**：已被授權自行決定的可逆選擇；記錄理由、影響與驗證方式。
- **deferred**：明確延後且不屬本版；同步放入 out of scope。

定義確定後更新 CONTEXT；同一術語只保留一個定義。只有需留下重大取捨理由時才新增 ADR。日常命名與小幅調整不需要獨立 ADR。

## 何時結束訪談

能寫出主流程、重要例外、MVP 邊界和可衡量的成功條件，且相關 blocking 已解決，就進入 Spec。不可把「使用者沒回覆」當成採納選項；可先寫已知部分草稿，不實作依賴未決答案的行為。

## 產出本專案的工作流程摘要

盤點與訪談後，更新目標根目錄的 `PROJECT_WORKFLOW.md`，讓使用者可以直接審閱「本專案將如何工作」。初次複製的入口只是骨架，完成盤點後才能視為專案化摘要。

- 指出本次範圍與適用階段，以及各階段的產物和通過條件；只要求規劃時明確指出本次停在哪裡。
- 說明適合本專案的驗證方式：例如 CLI 的程序輸入輸出、Web 的 API／瀏覽器驗收，或純文件的連結檢查；不適用的方式簡短說明原因。
- 連到 PROJECT 的真實命令與授權、SPEC 的測試邊界、STATE 的續作位置；詳細值仍由原文件負責，不在摘要維護第二份。
- 只填查證過的事實與已定案選擇；待決項標記為草稿並連到 BRIEF。保留指向本機 Skill 的入口。

Spec 與 Task 寫完後，再核對摘要是否與它們一致，與規劃文件一起呈現。需求或工作方式改變時同步更新受影響摘要；日常進度只更新 STATE。
