# Code Review：Spec 與程式品質

每張 Task 的實作與相關測試完成後執行 Review，修正後再審查。讀取 REVIEW 範本，分開保留兩個面向的發現，不能用一方通過抵銷另一方失敗。

## 固定審查範圍

使用開工前保存的基準。至少記錄基準 SHA／快照、目前 SHA 或檔案雜湊、比較方式、納入檔案、排除的既有修改及理由。

- 以 commit SHA 作基準且已有提交：`git diff <base-sha> HEAD` 檢查已提交差異。
- `git diff HEAD` 檢查目前追蹤檔案中尚未提交的內容，包含 staged 與 unstaged 的合計結果；需要辨別兩者時再分別查看 `git diff --cached` 與 `git diff`。
- `git ls-files --others --exclude-standard` 列出未追蹤檔案，逐一閱讀與本張相關的新程式、測試及文件。一般 diff 不會顯示它們。
- 任務前已有未提交修改時，以上差異不足以歸因；對照開工快照，說明本次新增／修改的部分，不把使用者原有內容算成自己的交付。
- 無 Git 或尚無第一個 commit 時，使用前後快照、檔案清單與完整新增檔案內容審查。不能因沒有 diff 就宣稱審查通過。

每次重審記錄新增修正與最後被審版本；程式又改動時，舊 review 結论不能直接當最新結果。

## A. Spec Review

逐條對照本張 AC 與實際程式、測試：

- 有無漏做、只做一部分、做錯條件或多做未要求行為？
- 例外、權限、資料狀態與公開契約符合 Spec 嗎？
- 測試是否真的驗證 AC，是否存在只靠 mock 的假通過？
- 相關 AC 跨多張 Task 時，本張承諾是否完成，整合驗證責任是否清楚？

每個問題引用 AC ID 或規格段落，描述具體觸發情境和可觀察後果。找不到 Spec 時標「無法完成 Spec Review」，回到補規格或向使用者釐清；不得視為兩軸都通過。

## B. 品質 Review

先讀專案適用的程式規範，再檢查實際差異中的正確性、可維護性與適用風險：

- 錯誤處理、資源釋放、輸入驗證、資料一致性；有相關功能時檢查授權、機密、併發與外部副作用。
- 測試能否辨認退化、是否依賴 private 實作、是否不穩定或污染彼此。
- 模組責任與公開介面是否清楚，有沒有無需要的抽象、重複邏輯或難理解命名。
- 是否符合既有維護習慣，是否引入會妨礙部署或相容性的變更。

工具已能判定的格式／lint 交給工具；設計偏好註記為建議，不能偽裝成已證實 bug。不為湊數發現問題。

## 執行方式

預設由同一 AI 分兩次、使用分開的檢查清單完成，報告標為 `self-review`。若使用者明確要求獨立代理審查，且環境支援與允許，才將相同基準分交獨立 reviewer；主 AI 彙整後修正。沒有獨立 reviewer 就不宣稱獨立審查。

## 問題與結案

每項發現包含 ID、面向、檔案／行號、觸發條件、影響、修正建議、處理狀態與驗證證據。

| 等級 | 處理方式 |
| --- | --- |
| blocking | AC 不符、可重現 bug、必要測試不過、相關安全／資料破壞問題；修正並重驗前不能 done |
| advisory | 無功能錯誤的維護／風格建議；衡量本張範圍後修正或記錄延後理由 |

修正行為缺陷先補能捕捉它的回歸測試，再 Red → Green。純重構從綠色基線開始，做最小修改並保持測試通過；不趁機改變 Spec。重跑受影響檢查，重審修正，直到 blocking 歸零。

報告允許「未發現問題」，但必須附已檢查範圍和限制。語法檢查通過、測試通過或自我描述「已 review」都不能單獨取代本節。
