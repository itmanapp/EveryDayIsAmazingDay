# ADR-001：從零重建，並以單一 SPEC-001 涵蓋全部範圍

- 狀態：accepted
- 日期：2026-09-24
- 關聯 Spec／AC／Task：SPEC-001 v0.4 全部；TASK-001～TASK-037

## 背景

需求來源 `docs/architecture/ENGINEERING-REPORT.md` 描述的是另一個已交付的專案（Git tag `V1.0`／commit `4e6c2a7`，位於 `~/桌面/DSH/ediaad`），其中 v0.2 已實作完成（185 個測試），v0.3 已定案未實作。本次工作區 `EveryDayIsAmazingDay` 是空目錄。使用者被詢問後選擇「本工作區，從零重建」與「範圍：全部（Web G1–G11 ＋ 多市場 ＋ 授權 ＋ 更新 ＋ 通知 ＋ Cloudflare 後端）」。

## 選項與取捨

| 選項 | 優點 | 代價 |
| --- | --- | --- |
| 沿用既有 `~/桌面/DSH/ediaad` 續作 v0.3 | 保留 185 個測試與已驗證的核心引擎；工作量最小 | 需授權寫入工作區外的目錄；核心引擎無法依新需求調整結構；v0.2 的設計債（全域 `ALLOWED_INTERVALS`、記憶體去重）需另外重構 |
| 複製 v0.2 程式碼到本工作區再擴充 | 保留既有驗證成果 | 產生兩份會分岔的程式碼；複製來的測試與文件會與新 SPEC 不一致 |
| **從零重建（採用）** | 程式與文件同源；模組邊界可依 v0.3 需求一次設計到位（`Source` 介面、SQLite、可注入外部效果）；工作區乾淨 | 需重新實作核心引擎並重寫測試；短期工作量最大 |
| 拆成 SPEC-001（核心）＋ SPEC-002（v0.3）兩份 | 版本界線清楚 | 兩份 Spec 需互相引用與同步，AC 與 Task 歸屬變複雜；本專案沒有「v0.2 已交付」的歷史包袱需要保留 |

## 決策

從零重建，並以**單一 SPEC-001** 涵蓋全部範圍（66 項 AC、37 張 Task）。理由：

1. 既有專案只作為**設計與領域知識來源**，其缺陷紀錄（F-001 資料結構不一致、F-002 契約不一致、F-003「沒有結果」與「無法得到結果」未區分）直接轉成本專案的回歸 AC（AC-004、AC-013、AC-025），因此不必沿用程式碼也能保住教訓。
2. v0.3 要求廢除全域 `ALLOWED_INTERVALS`（報告第 7.1 節）並把提醒狀態落地；這些是結構性變更，重建比改造更乾淨。
3. 單一 Spec 讓 AC → Task → 測試的對照只有一份權威，符合本流程的驗證契約。

## 後果與調整條件

- 接受代價：核心引擎（約 900 行純計算）與其測試需重新撰寫；交付時間比續作長。
- 接受代價：既有 185 個測試不構成新專案的證據，只能作設計參考；新專案必須自行產生測試證據。
- 重訪條件：若使用者改變主意要沿用既有程式碼，需走需求變更流程，重新評估 AC-030（`Source` 介面）與 AC-039（SQLite 去重）對既有模組的影響。
