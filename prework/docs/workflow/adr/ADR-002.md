# ADR-002：授權驗章採純 Python Ed25519，不引入 cryptography

- 狀態：accepted
- 日期：2026-09-24
- 關聯 Spec／AC／Task：AC-054；TASK-029

## 背景

v0.3 的授權子系統需要在客戶端驗證伺服器以 Ed25519 簽發的租約（報告第 6.4 節）。專案的核心優勢是「一次安裝、零新增依賴」，執行期依賴目前只有 `numpy` 與 `pandas`。2026-09-24 實測本機系統 Python 已安裝 `cryptography 41.0.7`，但 `.venv` 是隔離環境，不會自動取得它。

## 選項與取捨

| 選項 | 優點 | 代價 |
| --- | --- | --- |
| 加入 `cryptography` 依賴 | 實作最省事、經過廣泛驗證 | 新增一個二進位 wheel 依賴（報告實測 4.7MB、免編譯）；與「零新增依賴」原則衝突；在無 wheel 的平台會變成編譯問題 |
| 直接使用系統 Python 的 `cryptography` | 不新增 `.venv` 依賴 | 依賴系統套件狀態（本機有、別台未必）；破壞 `.venv` 的隔離與可重現性；`venv --without-pip` 路徑下更不可靠 |
| **純 Python Ed25519（採用）** | 零新增依賴；只用 `hashlib.sha512` 與任意精度整數；可用 RFC 8032 官方向量作確定性 oracle | 需自行實作並承擔正確性風險；效能較低（報告實測 2000 次模逆運算 0.206 秒，單次驗章充裕） |
| 以 HMAC 對稱簽章取代 | 實作更簡單 | 金鑰必須內嵌客戶端，等於沒有簽章；任何客戶端都能自行簽發租約 |

## 決策

採純 Python Ed25519 驗章，只用標準庫，並以 **RFC 8032 官方測試向量**作為正確性 oracle（AC-054）。分工維持報告的設計：**Worker 端以 WebCrypto 簽章**（私鑰留在伺服器），**客戶端以純 Python 驗章**。

## 後果與調整條件

- 接受代價：驗章程式碼約 100～150 行，屬安全敏感程式碼，必須有向量測試與 Review；不得自行發明曲線運算，需依 RFC 8032 的參考流程實作。
- 接受代價：效能較 `cryptography` 差，但單次驗章在啟動路徑上不構成瓶頸。
- 已知的架構事實（非本 ADR 可解）：客戶端授權只能防君子；`.py` 檔可被修改，控制力應放在「更新」（伺服器不發就拿不到）。
- 重訪條件：若未來需要大量簽章驗證（例如批次驗證多張租約）或需要其他曲線，再評估引入 `cryptography`；報告已確認該 wheel 可用，替換成本低。
